# Claude Code Harness - Canonical Conversion and Runtime Specification

This document is the maintained contract for the Claude Code harness in this repository. It defines source ownership, deterministic conversion, generated outputs, Claude Code discovery paths, validation, and known loss boundaries.

Validated against Claude Code **2.1.251** on **2026-08-31**. Dated first-party and runtime evidence is recorded in [CLAUDE-CODE-VALIDATION.md](CLAUDE-CODE-VALIDATION.md).

## 1. Source of truth

Reusable primitive content is authored under `harness/github-copilot/`. The directories below are generated by `harness/claude-code/scripts/convert_from_copilot.py`:

- `harness/claude-code/agents/`
- `harness/claude-code/rules/`
- `harness/claude-code/skills/`
- `harness/claude-code/commands/`
- `harness/claude-code/hooks/`
- `harness/claude-code/plugins/`
- `harness/claude-code/settings.json`
- `.claude-plugin/marketplace.json`

Do not edit those outputs directly. Maintained Claude-specific source consists of:

- `harness/claude-code/scripts/`
- `harness/claude-code/manifests/`
- this specification
- `docs/CLAUDE-CODE-VALIDATION.md`

`CLAUDE-CODE-CATALOG.md`, `CLAUDE.md`, and the declared `.claude/` files are generated distribution surfaces.

## 2. Primitive routing

| Canonical Copilot source | Claude Code output | Claude Code role |
| --- | --- | --- |
| `agents/<name>.agent.md` | `agents/<name>.md` | Subagent |
| `instructions/<name>.instructions.md` | `rules/<name>.md` | Project rule |
| `skills/<name>/SKILL.md` | `skills/<name>/SKILL.md` | Skill |
| `prompts/<name>.prompt.md` | `commands/<name>.md` | Legacy-compatible custom command |
| `plugins/<name>/plugin.json` | `plugins/<name>/.claude-plugin/plugin.json` | Plugin |
| `hooks/<name>/hooks.json` | `hooks/<name>/hooks.json` | Reusable hook package |

Custom command files remain supported, but Claude Code documentation now treats commands as part of the skills system and recommends skills for new reusable procedures. Conversion keeps prompts as commands because both are explicit, single-file user actions; it does not claim that VS Code runtime inputs or tools survive unchanged.

## 3. Discovery and installation

| Type | Project | User | Plugin |
| --- | --- | --- | --- |
| Subagent | `.claude/agents/**/*.md` | `~/.claude/agents/**/*.md` | `<plugin>/agents/**/*.md` |
| Rule | `.claude/rules/**/*.md` and `CLAUDE.md` | `~/.claude/CLAUDE.md` | Not a plugin component |
| Skill | `.claude/skills/<name>/SKILL.md` | `~/.claude/skills/<name>/SKILL.md` | `<plugin>/skills/<name>/SKILL.md` |
| Command | `.claude/commands/*.md` | `~/.claude/commands/*.md` | `<plugin>/commands/*.md` |
| Hook | `.claude/settings*.json` | `~/.claude/settings.json` | `<plugin>/hooks/hooks.json` |
| Plugin | Registered marketplace or `--plugin-dir` | Registered marketplace | `.claude-plugin/plugin.json` |

The repository marketplace lives at `.claude-plugin/marketplace.json`. Its local plugin sources point to self-contained packages under `harness/claude-code/plugins/`.

The installed-copy manifest at `harness/claude-code/manifests/installed-primitives.json` publishes the repository's own `CLAUDE.md`, selected rules, subagent, skills, command, project settings, and enabled hook packages. Synchronize it with:

```sh
python3 harness/github-copilot/scripts/sync_installed_primitives.py \
  --manifest harness/claude-code/manifests/installed-primitives.json
```

## 4. Subagents

Generated subagents require:

- a kebab-case `name` matching the filename;
- a non-empty `description`;
- a non-empty Markdown system prompt body.

Supported generated fields are `name`, `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `effort`, and `isolation`.

Plugin-shipped subagents do not support `permissionMode`, `mcpServers`, or `hooks`. The converter omits unsupported plugin fields, and the validator rejects them if they appear.

`tools` is a Claude Code allow-list. Copilot tool names are mapped only when there is a documented Claude equivalent. Unknown or unsupported source tools are reported by the converter and omitted rather than invented.

## 5. Rules and CLAUDE.md

Copilot instructions become Claude project rules:

- `applyTo` becomes a `paths` list.
- Universal instructions omit `paths` and apply globally.
- Copilot `description` is preserved as a visible scope note because Claude rule frontmatter documents only `paths`.

Repository-wide governance is also copied to root `CLAUDE.md` through the installed-copy manifest. More specific rules live under `.claude/rules/`.

## 6. Skills and commands

Skills preserve portable Agent Skills content and documented Claude Code extensions. The converter maps `allowed-tools` and `disallowed-tools` to Claude tool names, preserves supported invocation fields, and copies bundled resources.

Exact portable Markdown references to `web_fetch` and `web_search` are converted to Claude Code's `WebFetch` and `WebSearch` tool names. Other prose is preserved.

Commands use the same documented frontmatter family as skills except fields Claude ignores for command files. The filename is the invocation name.

Generated skill, command, and plugin payloads exclude:

- `.DS_Store`
- `__pycache__/`
- `*.pyc`
- `obj/`
- `bin/`

These are local or build artifacts, not portable primitive resources.

Two workspace-kit skills intentionally publish GitHub Copilot customizations. Their generated Claude plugins retain the required raw Copilot package content under `copilot-components/`, outside Claude component discovery, and the generated publisher scripts resolve sources from that compatibility payload. This preserves the documented cross-harness publishing behavior without registering duplicate Copilot agents or skills as Claude components.

## 7. Plugins and marketplace

Each generated plugin is self-contained. Claude Code automatically discovers conventional component directories, so generated manifests contain identity and publication metadata rather than Copilot component paths.

The plugin manifest is `plugins/<name>/.claude-plugin/plugin.json`. Plugin skills, agents, commands, hooks, and MCP configuration remain inside that plugin root because marketplace installation copies or caches the package independently.

The generated marketplace must pass:

```sh
claude plugin validate --strict .claude-plugin/marketplace.json
```

When Claude Code is available, validate plugin packages with `claude plugin validate --strict <plugin-path>`. Deterministic CI does not install Claude Code and therefore uses the repository Python validator.

## 8. Hooks

Copilot hook events are converted only when `HOOK_EVENT_MAP` defines a Claude Code equivalent. Unsupported events fail conversion rather than disappearing silently.

Project hook scripts resolve through `${CLAUDE_PROJECT_DIR}`. Plugin hook scripts resolve through `${CLAUDE_PLUGIN_ROOT}`. Environment variables and working directories are translated into the command string because Claude command-hook fields differ from the Copilot hook schema.

The converter reads the repository's installed Copilot hook activation policy from `.github/hooks/*.json`. It aggregates the four hooks that do not declare `disableAllHooks: true` into `harness/claude-code/settings.json` and the installed-copy manifest publishes their packages under `.claude/hooks/`:

- `dependency-license-checker`
- `governance-audit`
- `secrets-scanner`
- `session-logger`

The four intrusive Copilot hooks that ship disabled remain inactive in Claude Code: `attester-import-check`, `fix-broken-links`, `session-auto-commit`, and `tool-guardian`.

The validator accepts the hook events and handler fields documented for Claude Code 2.1.251, including `PreModelSwitch` and `PostModelSwitch`. Generated packages currently use only events reachable from the canonical Copilot hook model.

## 9. Generated catalog

`CLAUDE-CODE-CATALOG.md` inventories generated subagents, rules, skills, commands, plugins, and hooks. Regenerate it after conversion:

```sh
python3 harness/claude-code/scripts/generate_catalog.py
```

The catalog is descriptive. It does not prove runtime activation or semantic equivalence.

## 10. Validation contract

Run the full Claude harness gate:

```sh
python3 harness/claude-code/scripts/convert_from_copilot.py --check
python3 harness/claude-code/scripts/validate_primitives.py --strict
python3 harness/claude-code/scripts/generate_catalog.py --check
python3 harness/github-copilot/scripts/sync_installed_primitives.py \
  --manifest harness/claude-code/manifests/installed-primitives.json --check
```

The gates prove:

- generated output matches canonical Copilot sources;
- generated frontmatter, tools, hooks, plugin manifests, and marketplace structure satisfy the maintained contract;
- the catalog matches the generated tree;
- declared `CLAUDE.md`, `.claude/settings.json`, hook scripts, and other `.claude/` copies exist and match their generated sources.

They do not prove that every converted workflow has identical semantics on both products. Surface-specific tool loss, prompt runtime inputs, MCP availability, authentication, external services, and interactive behavior require targeted runtime tests.

## 11. Precedence

1. Dated runtime evidence in `docs/CLAUDE-CODE-VALIDATION.md`.
2. This specification.
3. Deterministic converter and validator behavior.
4. Generated catalog and installed copies.

If evidence contradicts this specification, update the specification and converter before regenerating dependent outputs.
