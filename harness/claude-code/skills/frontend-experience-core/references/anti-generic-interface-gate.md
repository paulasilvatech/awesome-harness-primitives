# Anti-generic interface gate

Evaluate the implemented or proposed experience against observable evidence.

| Gate | Pass evidence | Block condition |
| --- | --- | --- |
| Product identity | Real nouns, statuses, units, permissions, data, and workflow shape are visible. | Replacing the logo could make the interface belong to an unrelated product. |
| Hierarchy | Visual weight and order follow the user's decision sequence. | Every region has equal weight or decoration leads the task. |
| Containers | Cards frame repeated comparable items, modals, or real tools. | One-off sections or cards-inside-cards exist only to fill space. |
| Controls | Every visible action works, is honestly unavailable, or is absent. | A convincing-looking control is inert or has no failure state. |
| State completeness | Applicable loading, empty, partial, error, offline, success, disabled, and access states exist. | Only the happy path is designed or implemented. |
| Adaptation | Content and controls change priority and behavior across supported conditions. | Mobile merely stacks every desktop region. |
| System integrity | Existing tokens and components are reused; additions are justified and reusable. | A parallel mini design system appears for one feature. |
| Evidence | Acceptance IDs map to tests or documented manual verification. | Completion is based on taste, screenshots, or checklist claims alone. |

References may transfer hierarchy, density, navigation, and interaction decisions. Never copy branding, proprietary content, imagery, or exact layouts.
