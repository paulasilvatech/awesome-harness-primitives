# PCF Canvas App Conventions — Secure Enablement and Maker Use

These instructions apply to Power Apps component framework files intended for canvas app use. They are authoritative for canvas app security review, environment prerequisites, feature enablement, Studio warnings, import behavior, component properties, deletion, and update conventions; general PCF component, events, and Fluent theming instructions win for implementation details they own. Code components can access security tokens and data in Power Apps Studio, so only trusted and validated solutions should be opened, imported, or made available to makers.

## Security and Trust

- Treat canvas app code components as code that may not be generated by Microsoft and may access security tokens and data when rendered in Power Apps Studio.
- Validate all code components before importing them into an environment.
- Administrators and system customizers should review components and make them available to makers only after validation.
- Treat the Power Apps Studio warning about potentially unsafe code as meaningful; the vulnerability does not exist when playing the canvas app, but Studio can expose tokens.
- Expect the `Default` publisher to appear when importing code components through an unmanaged solution or when using `pac pcf push`.

## Prerequisites and Environment Enablement

- Require a Power Apps license for PCF canvas app use.
- Require system administrator privileges to enable the Power Apps component framework feature in the environment.
- Enable the Power Apps component framework feature for canvas apps in each environment where makers need to use code components.
- Remember that the component framework feature is enabled by default for model-driven apps, not necessarily for canvas apps.
- Use Power Apps Admin Center environment settings under Product features to enable `Power Apps component framework for canvas apps`.

## Component Import and Maker Configuration

- Import the solution `.zip` containing code components into Microsoft Dataverse before adding the component to a canvas app.
- Add components in Power Apps Studio through **Add (+)**, **Get more components**, the **Code** tab, and **Import**.
- Use **Code components** in the insert pane after import to place the component on a screen.
- Prefer the current **Get more components** flow over **Insert > Custom > Import component**, because the latter is scheduled for removal.
- Expect code component properties to appear on the Properties tab.
- Re-import existing components; existing code components can be re-imported with an updated manifest `version` when new properties need to appear in the default Properties tab; existing properties can remain available on Advanced properties.

## Deletion and Updates

- Delete a code component from a canvas app through Tree view, the screen containing the component, More (...), and Delete.
- Save the app after deleting a component so the change persists.
- Change the manifest `version` whenever component code changes and runtime updates need to appear.
- Expect existing code components to update only when the app is closed and reopened in Power Apps Studio.
- Publish all customizations in the updated solution before expecting component updates to appear.
- Do not rely on deleting and adding a component back to update it.

## Implementation Boundaries

- Use Microsoft Power Platform CLI for professional component development.
- Check each API for canvas app availability because certain APIs might not be available in canvas apps.
- Check code component limitations before implementation.
- Use the general PCF code component conventions for manifest, lifecycle, resources, `notifyOutputChanged`, `getOutputs`, and `destroy` behavior.

## Good / Bad Examples

The examples below illustrate safe update and import behavior.

**Good:**

```text
Validate the component solution, import the solution .zip into Dataverse, update the manifest version for changed code or properties, publish customizations, close and reopen Power Apps Studio, then let makers import from the Code tab.
```

Why: The sequence respects trust review, solution import, manifest versioning, publication, and Studio refresh behavior without exposing unvalidated code.

**Bad:**

```text
Use pac pcf push from an unmanaged solution, ignore the Default publisher warning, and tell makers to delete and re-add the component when changes do not appear.
```

Why: The behavior bypasses review signals, relies on an unmanaged publisher, and misunderstands how canvas apps refresh existing components.

## Conventions

| Rule | Rationale |
| --- | --- |
| Review and validate code components before environment import | Studio can expose tokens and data to component code |
| Enable PCF for canvas apps per environment with administrator privileges | Canvas app support is environment-level configuration |
| Import solution `.zip` files into Microsoft Dataverse before maker use | Canvas apps consume code components through solutions |
| Use **Get more components** and the **Code** tab in Power Apps Studio | The older **Insert > Custom > Import component** path is scheduled for removal |
| Update the manifest `version` for changed components and properties | Studio uses versioning and reopen behavior to refresh existing components |
| Publish all customizations before expecting updates | Unpublished solution changes do not appear to app makers |
| Check API availability and limitations for canvas apps | Some PCF APIs differ by host |

## Do / Do Not

| Do | Do not |
| --- | --- |
| Trust only reviewed component solutions | Open untrusted component code in Power Apps Studio |
| Require a Power Apps license and system administrator enablement | Assume model-driven app defaults enable canvas apps |
| Use the Admin Center Product features setting | Skip environment-level feature configuration |
| Import the solution before adding the component to an app | Add a component that has not been imported into Dataverse |
| Change manifest `version` when code changes | Expect delete-and-add behavior to refresh existing components |
| Reopen Power Apps Studio after updates | Assume Studio hot-reloads existing code components |
| Check limitations and host API availability | Assume every PCF API works in canvas apps |

## Checklist Before Opening a PR

- [ ] Component code intended for canvas apps has been reviewed as trusted code before import.
- [ ] The target environment has the canvas app PCF feature enabled by a system administrator.
- [ ] Required Power Apps licensing and Microsoft Dataverse solution import assumptions are documented.
- [ ] Makers can add the component through **Get more components** and the **Code** tab.
- [ ] The manifest `version` changes when code or properties change.
- [ ] Updated solution customizations are published before testing Studio refresh behavior.
- [ ] The app is closed and reopened in Power Apps Studio when verifying updates.
- [ ] Canvas app API availability and PCF limitations have been checked.
